# Задача: разделение логов Patroni и PostgreSQL

## Исходные данные

- Кластер **Patroni + PostgreSQL 16**, **production**, со стандартными (дефолтными) настройками логирования.
- Сейчас логи Patroni и логи PostgreSQL пишутся **в один поток**:
  - Patroni по умолчанию (секция `log` в `patroni.yml` отсутствует) пишет свои сообщения в `stderr`;
  - PostgreSQL при `logging_collector = off` тоже пишет в `stderr`, который Patroni наследует от родительского процесса;
  - systemd перехватывает `stdout/stderr` юнита `patroni.service` и складывает всё в journal.
- Как следствие, оба типа логов читаются только через `journalctl -u patroni`, перемешаны между собой и не имеют независимой ротации и независимого уровня детализации.

## Что нужно сделать

Написать конфигурацию, которая **разделяет логи Patroni и логи PostgreSQL** на два независимых потока:

1. Логи Patroni — в отдельный файл/каталог с собственной ротацией и уровнем логирования.
2. Логи PostgreSQL — в отдельный каталог через встроенный сборщик логов (`logging_collector`), с собственным форматом строки, ротацией и уровнем логирования.
3. Исключить попадание логов PostgreSQL в journal вместе с логами Patroni.

## Ограничения production-кластера

- **Простой недопустим.** Единственный требующий рестарта параметр — `logging_collector`; раскатка идёт
  поочерёдно: сначала реплики, затем переключение роли (`switchover`) и бывший лидер.
  Прямой `systemctl restart patroni` на лидере запрещён — он вызывает незапланированный failover.
- **Не менять в рамках этой задачи ничего, кроме логирования.** Параметры `KillMode`, `TimeoutStopSec`,
  `Restart` в юните, настройки репликации и памяти — вне области изменений.
- **Логи не должны приводить к отказу СУБД.** Каталоги логов — на отдельной файловой системе
  (не на той, где `PGDATA` и не на `/`), с настроенным удержанием и мониторингом свободного места.
- **Ротация без потери данных.** Недопустимы комбинации параметров, при которых действующий лог-файл
  перезаписывается или обрезается (`log_truncate_on_rotation` в паре с неуникальным `log_filename`,
  внешний `logrotate` с `copytruncate` поверх `logging_collector`).
- **Объём логов ограничен сверху.** Для Patroni — числом и размером файлов, для PostgreSQL — политикой
  удержания; оба значения посчитаны и укладываются в выделенный раздел.
- **Изменения обратимы.** Для каждого шага есть процедура отката без рестарта там, где это возможно.
- **Изменения вносятся через DCS** (`patronictl edit-config`) с просмотром diff, а не правкой
  `postgresql.conf` на узлах и не `--force` вслепую.

## Артефакт

Создать файл `config.md`, в котором зафиксированы **все параметры логирования** в виде таблицы:

| Параметр | Стандартное значение | Новое значение |

Таблица должна покрывать:

- параметры секции `log` в `patroni.yml` (логирование самого Patroni);
- параметры `postgresql.parameters` в `patroni.yml` (логирование PostgreSQL 16);
- относящиеся к делу настройки systemd-юнита `patroni.service`.

Дополнительно в `config.md` должны быть: порядок раскатки по узлам, процедура отката,
политика удержания и расчёт объёма, подготовка ОС (каталоги, права, SELinux) и проверки.

## Критерии приёмки

- `journalctl -u patroni` содержит только сообщения Patroni и systemd.
- Логи Patroni лежат в собственном каталоге и ротируются средствами Patroni.
- Логи PostgreSQL лежат в собственном каталоге и ротируются средствами `logging_collector`.
- Для каждого изменённого параметра в `config.md` указано стандартное и новое значение.
- Явно указано, какие параметры требуют `restart`, а какие применяются по `reload`.
- `patronictl list` не показывает `pending_restart` после завершения раскатки.
- Ни один узел не терял роль лидера вне запланированного `switchover`.
